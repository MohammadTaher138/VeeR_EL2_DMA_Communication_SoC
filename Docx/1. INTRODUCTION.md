# 1. INTRODUCTION

## 1.1 Project Overview

The proposed project is a **RISC-V VeeR EL2 based Communication System-on-Chip (SoC) with DMA-Accelerated SPI and I²C communication**. The main objective of the project is to design and verify an RTL-based SoC in which a VeeR EL2 RISC-V processor controls communication peripherals such as SPI and I²C, while a dedicated DMA Controller performs bulk data movement between the communication peripherals and the processor's Data Closely-Coupled Memory (DCCM).

In a conventional processor-controlled communication system, the CPU is responsible for repeatedly reading data from or writing data to peripheral registers. For example, during a large SPI or I²C data transfer, the processor may have to handle each byte or word individually. This requires repeated load/store operations, polling or interrupt servicing, and software execution for data movement. As the amount of communication data increases, a considerable portion of the processor's execution cycles is consumed by repetitive data-transfer operations rather than by the actual application.

The proposed architecture addresses this limitation by introducing a **Direct Memory Access (DMA) Controller**. Once the processor configures the required peripheral and programs the DMA transfer descriptor, the DMA Controller autonomously transfers data between the selected peripheral FIFO/data register and a buffer located in the VeeR EL2 DCCM. The processor is therefore not required to intervene for every byte or word. Instead, the processor is notified mainly when the transfer is completed or when an error occurs.

---

## 1.2 Problem Statement

Embedded systems frequently communicate with external devices using serial interfaces such as **SPI and I²C**. These interfaces are commonly used for sensors, memories, ADCs, DACs, displays and other peripheral devices.

The main problem considered in this project is the inefficient use of processor cycles during continuous or high-volume data transfers.

In a CPU-driven communication architecture, the general operation is:

1. The processor configures the communication peripheral.
2. The processor initiates a transfer.
3. The peripheral produces or receives data.
4. The processor reads data from the peripheral or writes data to it.
5. The processor repeats this operation for every transfer unit.
6. The processor handles status checking or interrupts.
7. The processor finally processes the received data.

This approach works for small amounts of data, but it becomes inefficient when large blocks of data have to be transferred continuously.

The processor should ideally perform application-level processing rather than spend most of its execution time moving communication data. Therefore, the proposed architecture separates **control operations** from **bulk data movement**.

The CPU performs the control and configuration functions, while the DMA Controller performs the repetitive data-transfer operations.

---

## 1.3 Why DMA is Required

DMA is introduced to reduce processor involvement in repetitive data movement.

Without DMA, the processor would continuously perform operations such as:

- Reading received data from SPI/I²C.
- Writing transmit data to SPI/I²C.
- Checking peripheral status.
- Managing transfer counts.
- Updating memory addresses.
- Handling repeated peripheral interrupts.

With DMA, the processor performs these operations only during initialization/configuration. After configuring the DMA Controller, the DMA hardware can autonomously perform the required transfer.

The basic concept is:

**CPU configures → DMA transfers → DMA completes → CPU receives interrupt**

This provides a cleaner division of responsibilities:

| Component | Main Responsibility |
|---|---|
| VeeR EL2 Core | Application execution and system configuration |
| SPI Controller | SPI protocol communication |
| I²C Controller | I²C protocol communication |
| DMA Controller | Bulk data movement |
| DCCM | Storage of DMA source/destination buffers |
| PIC | Interrupt collection and prioritization |
| UART | Reporting status/results to host |
| AHB-Lite Interconnect | Control/status communication between CPU and peripherals |

The project therefore demonstrates how dedicated hardware can be used to accelerate communication while allowing the processor to continue executing application code.

---

## 1.4 Proposed Solution

The proposed solution consists of the following major functional blocks:

- **VeeR EL2 RV32IMC RISC-V processor core**
- **Instruction Closely-Coupled Memory (ICCM)**
- **Data Closely-Coupled Memory (DCCM)**
- **AHB-Lite system bus interconnect**
- **DMA Controller**
- **SPI Controller**
- **I²C Controller**
- **UART**
- **Programmable Interrupt Controller (PIC)**
- **System clock and reset infrastructure**
- **External SPI and I²C devices**
- **Host computer interface through UART**

The VeeR EL2 processor acts as the central processing element. It executes the embedded application, initializes the system, configures the peripherals and programs the DMA transfer descriptors.

The AHB-Lite system bus is used for processor-initiated access to the memory-mapped control and status registers of the peripherals and DMA Controller.

The important architectural feature is the **dedicated DMA slave port of the VeeR EL2 core**. Instead of making the DMA Controller access the DCCM through the normal CPU LSU bus path, the DMA Controller uses the dedicated DMA interface provided by the VeeR EL2 core to access the core-local ICCM/DCCM memory.

---

## 1.5 Role of the VeeR EL2 Processor

The VeeR EL2 is the central processor of the proposed SoC. It is an **RV32IMC RISC-V implementation**.

The processor is responsible for executing the embedded software and performing system-level control operations.

The CPU will:

1. Initialize the system.
2. Initialize required memory buffers.
3. Configure the SPI Controller when SPI communication is required.
4. Configure the I²C Controller when I²C communication is required.
5. Configure the DMA Controller.
6. Program the DMA transfer descriptor.
7. Enable required interrupt sources.
8. Start the required peripheral/DMA operation.
9. Continue executing other application code while DMA performs the transfer.
10. Receive an interrupt when DMA completes or reports an error.
11. Process the transferred data.
12. Use UART to report selected data and transfer status to the host.

Thus, the processor primarily performs **control and application processing**, rather than continuous data movement.

---

## 1.6 Role of the AHB-Lite System Bus

The AHB-Lite interconnect provides the main control/configuration communication path in the SoC.

The processor accesses the memory-mapped registers of:

- SPI Controller
- I²C Controller
- DMA Controller
- UART
- Other system peripherals

through this bus.

For example, when the processor wants to configure a DMA transfer, it performs memory-mapped writes to the DMA Controller registers. These registers contain the information required to perform the transfer.

The AHB-Lite path is therefore mainly used for **control and status transactions**, whereas the DMA slave port provides the dedicated path for bulk data movement between DMA and DCCM.

The peripheral registers are intended to reside in a non-cacheable, side-effect-marked memory-mapped region separate from the core-local ICCM/DCCM region.

---

## 1.7 Role of the DMA Controller

The DMA Controller is the main acceleration block of the proposed architecture.

It is configured by the processor through memory-mapped registers. The CPU provides a transfer descriptor containing information such as:

- Peripheral selection
- Transfer direction
- DCCM buffer address
- Transfer length
- Source/destination information as required by the design

After the DMA transfer is triggered, the DMA Controller autonomously performs the required data movement.

For a receive operation, the data flow is conceptually:

**External Device → SPI/I²C Controller → Peripheral FIFO/Data Register → DMA Controller → VeeR EL2 DMA Slave Port → DCCM**

For a transmit operation, the direction is reversed:

**DCCM → VeeR EL2 DMA Slave Port → DMA Controller → SPI/I²C Controller → External Device**

The DMA Controller also generates an interrupt when the transfer is completed or when an error occurs.

---

## 1.8 Why the VeeR EL2 DMA Slave Port is Important

A key architectural requirement of this project is the use of the **dedicated DMA slave port provided by the VeeR EL2 core**.

The DCCM is a core-local memory and is normally accessed by the processor. The VeeR EL2 architecture provides a dedicated interface through which an external bus master, such as the DMA Controller, can access the core's ICCM/DCCM.

This allows the DMA Controller to directly transfer communication data to or from the DCCM without requiring the CPU to copy the data.

However, the architecture imposes important access requirements.

DMA write accesses to ICCM/DCCM must be **32-bit or 64-bit aligned and appropriately sized**, because the memories use ECC and partial unaligned writes are not supported by the DMA interface. The design and verification environment must therefore ensure that DMA transactions satisfy these alignment and sizing requirements.

Another important consideration is arbitration between the processor's own DCCM accesses and DMA accesses. The VeeR EL2 architecture gives the core's DCCM accesses priority over the DMA slave port when the DMA FIFO is not full. Consequently, concurrent processor activity can influence the effective DMA transfer rate. The `mfdc.dqc` configuration field controls how long a blocked DMA access waits before requesting a pipeline bubble.

## 1.9 SPI Communication

The SPI Controller provides synchronous serial communication with an external SPI-compatible device.

The SPI block is responsible for handling the SPI communication signals and protocol operation, including:

- Serial clock
- Chip-select
- Transmit data
- Receive data

The controller contains transmit/receive data storage, such as FIFOs, that can interface with the DMA Controller.

For SPI reception, received data is placed into the SPI receive FIFO and then transferred by DMA into the DCCM buffer.

For SPI transmission, data stored in the DCCM buffer is transferred by DMA to the SPI transmit FIFO and subsequently transmitted to the external SPI device.

The SPI Controller can also generate interrupt events such as FIFO threshold or transfer completion events.

---

## 1.10 I²C Communication

The I²C Controller provides two-wire communication with I²C-compatible external devices.

The controller handles the required I²C communication operations, including:

- Start condition
- Device addressing
- Read/write operation
- Data transfer
- Acknowledgement
- Stop condition

The I²C data register/FIFO acts as the interface between the I²C communication logic and the DMA Controller.

For an I²C receive operation, data received from the external device is stored in the I²C data register/FIFO and subsequently transferred to the DCCM by DMA.

For an I²C transmit operation, the DMA Controller obtains data from the DCCM and provides it to the I²C Controller for transmission.

The I²C Controller also provides status and interrupt information to the processor through its registers and the PIC.

---

## 1.11 Role of DCCM

The **Data Closely-Coupled Memory (DCCM)** is used to store processor data as well as DMA communication buffers.

In this project, the DCCM can contain:

- SPI transmit buffers
- SPI receive buffers
- I²C transmit buffers
- I²C receive buffers
- Application data
- DMA-related data structures as required

The use of DCCM as the DMA buffer provides a direct data path between the communication peripherals and the processor's local memory.

Because DCCM is ECC-protected, DMA accesses must obey the required alignment and access-size restrictions.

Software must also avoid reading a DCCM buffer while the DMA transfer to that same buffer is still in progress, because the VeeR EL2 DMA interface does not provide an ordering guarantee for accesses to the same address. The software therefore reads the DMA buffer only after receiving the DMA completion indication.

---

## 1.12 Role of PIC and Interrupt Handling

The **Programmable/Platform-Level Interrupt Controller (PIC)** is responsible for collecting interrupt requests from the DMA Controller and communication peripherals.

Possible interrupt sources include:

- DMA transfer completion
- DMA transfer error
- SPI events
- I²C events
- Other supported peripheral events

The PIC prioritizes the interrupt sources and presents the appropriate interrupt to the VeeR EL2 processor.

This allows the processor to operate normally during DMA activity and respond only when software intervention is actually required.

For example:

**DMA transfer starts → CPU continues application execution → DMA completes → DMA generates interrupt → PIC receives interrupt → PIC signals CPU → CPU executes interrupt service routine**

This significantly reduces the need for continuous CPU polling.

---

## 1.13 Role of UART

UART provides a simple communication interface between the SoC and a host computer.

UART is not the primary high-speed data-transfer path of this architecture. Instead, it is mainly used for:

- Reporting system status
- Reporting DMA transfer completion
- Reporting errors
- Displaying received SPI/I²C data
- Debugging
- Observing system behavior during simulation and hardware execution

This makes UART particularly useful during verification because the host computer can observe whether the expected transfer occurred and whether the system generated the correct status information.

---

## 1.14 Overall System Operation

The complete system can be operated using the following sequence.

### Step 1: System Initialization

After reset, the VeeR EL2 processor starts execution from its instruction memory and initializes the required system components.

### Step 2: Buffer Initialization

The processor initializes the required DCCM memory locations that will be used as DMA source or destination buffers.

### Step 3: Peripheral Configuration

The processor configures either the SPI Controller or I²C Controller depending on the communication requirement.

### Step 4: DMA Configuration

The processor programs the DMA Controller with the required transfer information, including the peripheral selection, direction, DCCM address and transfer length.

### Step 5: Transfer Start

The processor enables/starts the required peripheral and DMA operation.

### Step 6: Autonomous Data Transfer

The DMA Controller performs the repetitive data movement without requiring the processor to service every byte or word.

### Step 7: Processor Continues Execution

While the DMA transfer is active, the processor can execute other application code, subject to the DCCM access/arbitration considerations defined by the VeeR EL2 architecture.

### Step 8: Transfer Completion/Error

When the transfer finishes, or if a transfer error occurs, the DMA Controller generates the corresponding interrupt.

### Step 9: PIC Processing

The PIC receives the interrupt request, prioritizes it and signals the VeeR EL2 processor.

### Step 10: Software Response

The processor executes the appropriate interrupt service routine, checks the DMA/peripheral status and processes the transferred data.

### Step 11: UART Reporting

The application can transmit status information or selected data to the host computer using UART.

This sequence demonstrates the main principle of the proposed architecture:

**Configure once → Transfer autonomously → Interrupt on completion/error → Process result**

## 1.15 What Needs to be Designed

The architecture requires the following major RTL blocks and interfaces to be designed/integrated:

1. **VeeR EL2 processor integration**
   - Integrate the faculty-provided VeeR EL2 core.
   - Connect its IFU and LSU interfaces appropriately.
   - Connect its dedicated DMA slave interface.

2. **ICCM/DCCM integration**
   - Provide instruction and data storage.
   - Ensure ECC-related access requirements are respected.
   - Provide appropriate DCCM access for both CPU and DMA.

3. **AHB-Lite interconnect**
   - Connect the processor's LSU master interface to the memory-mapped peripherals.
   - Implement appropriate address decoding.
   - Route read/write transactions to the selected peripheral.

4. **DMA Controller**
   - Implement configuration registers.
   - Implement transfer descriptor registers.
   - Implement transfer control logic.
   - Implement address generation.
   - Implement peripheral data movement.
   - Implement DCCM read/write operations through the DMA slave port.
   - Implement completion and error detection.
   - Generate DMA interrupts.

5. **SPI Controller**
   - Implement SPI control and status registers.
   - Implement transmit and receive data paths.
   - Implement FIFO operation.
   - Implement SPI serial interface.
   - Generate required interrupt events.

6. **I²C Controller**
   - Implement I²C control and status registers.
   - Implement I²C protocol state/control logic.
   - Implement data register/FIFO.
   - Implement SDA/SCL interface.
   - Generate required interrupt events.

7. **UART**
   - Implement transmit/receive functionality.
   - Provide status reporting to the host.

8. **PIC**
   - Connect DMA, SPI and I²C interrupt sources.
   - Provide interrupt prioritization and delivery to the core.

9. **Clock and Reset**
   - Provide system clocking and reset generation/distribution.

## 1.16 How the Architecture Should be Verified

The architecture must be verified at the RTL level using a dedicated testbench.

Verification should not be limited to checking whether SPI or I²C communication works independently. The complete interaction between the CPU, DMA, DCCM, peripherals, bus and interrupt system must be verified.

The verification should include:

### CPU and Bus Verification
- CPU-generated AHB-Lite transactions
- Peripheral address decoding
- Register read/write operations
- Correct control/status access

### SPI Verification
- SPI transmit operation
- SPI receive operation
- FIFO behavior
- SPI status
- SPI interrupt generation

### I²C Verification
- Start/stop operations
- Addressing
- Read/write transfer
- Data transfer
- Acknowledgement handling
- I²C status and interrupts

### DMA Verification
- DMA descriptor programming
- DMA read operation
- DMA write operation
- SPI-to-DCCM transfer
- DCCM-to-SPI transfer
- I²C-to-DCCM transfer
- DCCM-to-I²C transfer
- Transfer length handling
- Completion detection
- Error detection

### VeeR EL2 DMA Interface Verification
- 32-bit aligned DMA accesses
- 64-bit aligned DMA accesses where applicable
- Correct access sizing
- Correct DCCM addressing
- Arbitration with concurrent core DCCM accesses
- Correct behavior when DMA accesses are blocked

### Interrupt Verification
- DMA completion interrupt
- DMA error interrupt
- SPI interrupt
- I²C interrupt
- PIC interrupt routing
- Correct processor interrupt response

### System-Level Verification
The system should also be tested with and without CPU activity during an active DMA transfer. This is important because the project specifically aims to demonstrate that DMA can perform communication data movement while the processor is available for other application processing.

## 1.17 Main Objective

The overall objective of the architecture is to demonstrate a complete RTL-based communication SoC in which the **VeeR EL2 RISC-V processor provides software control**, while the **DMA Controller provides autonomous bulk data movement** between SPI/I²C communication peripherals and the processor's DCCM.

The project therefore combines:

**RISC-V Processing + Local Memory + AHB-Lite Control Path + DMA Data Path + SPI + I²C + PIC + UART**

The key architectural benefit is the separation of **control path and data path**. The processor configures and supervises the system, while dedicated hardware handles repetitive communication data movement.

The final system should demonstrate that DMA-based communication can reduce CPU involvement while maintaining a simple memory-mapped programming model and respecting the VeeR EL2 DMA slave-port access requirements.

---

## 1.18 Scope of the Architecture

The scope of this project covers the design and RTL verification of the complete communication subsystem consisting of the VeeR EL2 core, its core-local memories and DMA slave interface, AHB-Lite interconnect, DMA Controller, SPI Controller, I²C Controller, PIC and UART.

The architecture specifically focuses on **DMA-accelerated SPI and I²C data transfers** and on verifying the interaction between CPU execution and autonomous DMA operation.

The project will demonstrate:

**CPU Configuration → DMA Descriptor Setup → Peripheral Communication → DMA Data Movement → DCCM Storage → Interrupt → CPU Processing → UART Status/Result Reporting**

This provides a complete system-level demonstration of a RISC-V based communication SoC with hardware-assisted data movement.
